# Инструкции агенту: фронтенд subtracker

Эти правила действуют для любого ИИ-агента и человека, который пишет код в `frontend/`. Читать до начала работы: `spec.md` (поведение), `scenario.md` (сценарий), `design-system.md` (внешний вид), `ui-library.md` (компоненты), `generation-spec.md` (порядок работ).

## Стек

React + TypeScript + Vite, Tailwind CSS v4, shadcn/ui (Radix UI), react-hook-form + zod, react-router-dom, lucide-react, sonner. Тесты: Vitest, React Testing Library, user-event, MSW. Пакетный менеджер `npm`. Язык интерфейса русский.

## Структура

```
frontend/
  src/
    api/          клиент fetch, типы, ошибки, сессия (токены)
    components/
      ui/         компоненты shadcn/ui, только они
      ...         составные компоненты проекта
    pages/        Login, Register, Subscriptions
    lib/          вспомогательные функции (деньги, даты, периоды)
    test/         настройка тестов, MSW-обработчики, фикстуры
    index.css     тема: переменные CSS, шрифты
```

## Обязательные правила

1. **Компоненты.** Только из `src/components/ui` (shadcn/ui). Не писать свои кнопки, поля, диалоги, выбор. Перед работой назвать, какие компоненты будут переиспользованы. Подробно: `ui-library.md`.
2. **Оформление.** Цвета, шрифты и скругления только через переменные темы из `src/index.css`. Никаких жёстких цветов в компонентах и страницах. Внешний вид по `design-system.md`, включая раздел «Адаптация» (он главнее исходного описания стиля).
3. **Поведение.** Каждое правило из `spec.md` реализовано и покрыто тестом. Номер правила стоит в названии теста.
4. **API.** Вся работа с сервером в `src/api`. Имена полей `snake_case` превращаются в `camelCase` только там. Суммы приходят строками, даты строками `YYYY-MM-DD`. Токены хранит один модуль, остальной код их не трогает.
5. **Повторная отправка.** Во время запроса кнопка и поля заблокированы, повторный клик или Enter второй запрос не создают. Блокировка обязана работать и при быстром двойном вызове (флаг в обработчике, а не только `disabled` после перерисовки).
6. **Состояния.** У каждого экрана с данными есть загрузка, пустой результат, успех и ошибка. При ошибке введённые значения в форме остаются, пользователь может повторить.
7. **Доступность.** У каждого поля `label`. Ошибка связана с полем (`aria-describedby`, `aria-invalid`), общая ошибка формы объявляется (`role="alert"`). Основной сценарий проходится только с клавиатуры. Видимый фокус на любом элементе управления. Контраст границ полей не ниже 3:1, текста не ниже 4,5:1.
8. **Движение.** Анимации (дрейф свечения) отключаются при `prefers-reduced-motion: reduce`.
9. **Адаптивность.** На ширине 360px нет горизонтальной прокрутки, элементы управления доступны.
10. **Секреты.** Никаких ключей и паролей в коде и репозитории. Адрес API из `VITE_API_URL`.

## Тесты

- Проверяют **видимое поведение**: что пользователь видит и может сделать, а не наличие компонентов в коде.
- Запросы к серверу подменяются через MSW: успех, пустой ответ, задержка, ошибка (401, 409, 422, 500). **Формат тестовых ответов совпадает с реальным API** (`spec.md`, раздел 7).
- Обязательны тесты: компоненты и взаимодействия, валидация (обязательные поля, неверный ввод, сообщения), состояния (загрузка, пусто, успех, ошибка), защита от двойной отправки (после двух быстрых кликов один запрос), один тест полного сценария (вход, добавление, запись в списке).
- Проверка качества: на сломанном поведении (например, убрать вывод ошибки) соответствующий тест должен падать.
- Все тесты запускаются одной командой `npm test` и проходят.

## Команды

```bash
npm install        # зависимости
npm run dev        # разработка, http://localhost:5173
npm test           # все клиентские тесты
npm run lint       # проверка кода
npm run build      # типы и сборка
```

## Git

- Коммиты **без** строки `Co-Authored-By`. Не пушить без прямой просьбы пользователя.
- Одна логическая задача на коммит, понятное сообщение.

## Чего не делать

- Не добавлять библиотеки сверх списка в «Стеке» без согласования.
- Не трогать `backend/` и `.github/` без отдельной просьбы.
- Не обновлять эталонные скриншоты ради зелёных тестов, если такие тесты появятся.
- Не писать код вне спецификации: если правила в `spec.md` не хватает, сначала дополнить спецификацию и сообщить.
