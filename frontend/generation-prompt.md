# Промпт для генерации фронтенда (практика 8, часть 2)

Это запрос агенту, который собирает интерфейс для всего API проекта (кроме импорта выписки, см. `spec.md`, раздел 11). Он покрывает часть 2 практики: библиотека компонентов и единое оформление, полный сценарий с настоящим API, соответствие макету, доступность, состояния и защита от повторной отправки. Тесты (часть 3) делаются следующим запросом.

```text
Роль: ты фронтенд-разработчик. Собери интерфейс сервиса Subtracker (трекер подписок) в каталоге frontend/ по спецификации и макету. Бэкенд (FastAPI) уже работает на http://localhost:8000.

Сначала прочитай, в таком порядке:
1. frontend/AGENTS.md: правила, стек, структура.
2. frontend/spec.md: поведение (разделы 1-10). Номера правил обязательны к выполнению.
3. frontend/scenario.md: основной сценарий.
4. frontend/design-system.md: стиль, цвета, шрифты, отступы, раздел «Адаптация» главнее остального.
5. frontend/ui-library.md: библиотека shadcn/ui и правила её использования.
6. frontend/fixtures.md: форматы данных API и общий набор данных.
7. Макет: https://claude.ai/artifact/NiEBXJbJF5FH1aRvnQDdBQ (кадры хранятся в виде файлов; внешний вид экранов входа, регистрации, списка и добавления подписки). Для экранов, которых нет на макете (обзор, диалоги изменения и удаления), используй те же компоненты и ту же систему.

Прежде чем писать код, назови компоненты shadcn/ui, которые будешь переиспользовать, и составные компоненты, которые создашь сам.

Требования (часть 2 практики):
A. Библиотека. Все кнопки, поля, подписи, выбор, диалоги, карточки, бейджи, уведомления, скелетоны берутся из shadcn/ui (src/components/ui). Своих аналогов не пиши. Новые компоненты ставь командой shadcn add.
B. Единое оформление. Цвета, шрифты (Manrope, Geist Mono), скругления, отступы задаются один раз переменными темы в src/index.css по design-system.md, раздел 8. В экранах и компонентах нет жёстких цветов и произвольных размеров.
C. Полный сценарий с настоящим API. Реализуй: вход, регистрацию (с автоматическим входом), список подписок с поиском, фильтрами, сортировкой, добавлением, изменением, приостановкой, удалением, и страницу «Обзор» (итоги, ближайшие списания, доли). Каждое действие приводит к реальному запросу к API и видимому результату. Токены хранит один модуль, при 401 один раз пробуется обновление токена.
D. Соответствие макету. Экраны входа, регистрации, списка, диалога добавления и узкий экран 390px выглядят как на макете, с теми же текстами сообщений из spec.md.
E. Доступность. У каждого поля есть label, ошибка связана с полем (aria-describedby, aria-invalid), общие ошибки объявляются (role="alert"). Основной сценарий проходится только с клавиатуры, фокус виден (белое кольцо), в диалогах фокус не уходит наружу и возвращается на кнопку-источник. На 360px нет горизонтальной прокрутки. Контраст по design-system.md, раздел 7. Анимации отключаются при prefers-reduced-motion.
F. Состояния. У каждого экрана с данными: загрузка (скелетон, aria-busy), пусто, успех, ошибка с кнопкой «Повторить». В формах при ошибке введённые значения остаются.
G. Повторная отправка. Пока форма отправляется, кнопка и поля заблокированы, а повторный клик или Enter второй запрос не создают. Защита должна работать при быстром двойном вызове (флаг в обработчике, не только disabled).

Технические условия: React + TypeScript + Vite, Tailwind CSS v4, shadcn/ui, react-hook-form + zod, react-router-dom, sonner, lucide-react. Формат данных API и преобразование snake_case в camelCase только в src/api. Адрес API из VITE_API_URL. Валюта берётся из профиля (GET /api/auth/me), суммы форматируются по ru-RU. Язык интерфейса русский. Не добавляй библиотек сверх списка.

Порядок работы: задачи G1-G9 из frontend/generation-spec.md. После каждой задачи запускай npm run lint и npm run build, в конце проверь работу на настоящем API (вход demo@example.com / demo-password). Коммиты без строки Co-Authored-By, ничего не пушь.

Когда закончишь, сообщи: что создано, какие решения принял сам, что не удалось сделать по описанию, что стоит добавить.
```
