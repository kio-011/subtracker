# Спецификация фронтенда subtracker (практика 8)

Макет задаёт внешний вид, эта спецификация задаёт поведение. Агент и тесты опираются на неё. Каждое правило проверяется тестом, номер правила стоит в названии теста.

Бэкенд: FastAPI, `http://localhost:8000` (адрес задаётся `VITE_API_URL`). Демо-вход после `./scripts/dev.sh --seed`: `demo@example.com` / `demo-password`.

## Область работ

Основной сценарий: **регистрация или вход → добавить подписку → увидеть её в списке**.

| Этап | Экраны | Статус |
|---|---|---|
| A (ядро для оценки) | вход, регистрация, список подписок, форма добавления | в работе |
| B | редактирование, удаление с подтверждением, фильтр и поиск | позже |
| C | обзор: итоги за месяц и год, доли по подпискам | позже |

Результат сценария: пользователь видит свой список подписок, и в нём новая подписка с названием, суммой, периодом оплаты и датой ближайшего списания. Всё нужное видно в самом списке, отдельной страницы или карточки подписки с деталями не требуется.

Вне области: страница подписки с подробностями, темы и языки, импорт выписки, Pro-функции.

## 1. Сессия и доступ

1.1. Токены хранятся в одном модуле (`localStorage`). Остальной код их не трогает.
1.2. Незалогиненный пользователь на `/subscriptions` перенаправляется на `/login` и видит сообщение «Войдите, чтобы продолжить».
1.3. Залогиненный пользователь на `/login` и `/register` перенаправляется на `/subscriptions`.
1.4. Если защищённый запрос вернул 401, клиент один раз пробует обновить токен (`POST /api/auth/refresh`) и повторяет запрос. Если не вышло, сессия сбрасывается, пользователь попадает на `/login` с сообщением «Сессия истекла, войдите снова».
1.5. Кнопка «Выйти» очищает токены и ведёт на `/login`.

## 2. Вход (`POST /api/auth/login`)

2.1. Поля «Email» и «Пароль» обязательны. Если пустые, запрос не отправляется, рядом с полем сообщение «Введите email» / «Введите пароль», фокус на первом пустом поле.
2.2. Во время отправки кнопка заблокирована и показывает «Входим…», поля заблокированы. Повторный клик или Enter второй запрос не создают.
2.3. При ответе 401 над кнопкой сообщение «Неверный email или пароль. Нет аккаунта? Зарегистрируйтесь» (со ссылкой на регистрацию). Сервер не отличает неизвестный email от неверного пароля, поэтому сообщение одно. Введённые значения остаются, пользователь может исправить и отправить снова.
2.4. При сетевой ошибке или 5xx сообщение «Не удалось связаться с сервером. Повторите попытку», значения остаются.
2.5. При успехе токены сохраняются, пользователь попадает на `/subscriptions`.

## 3. Регистрация (`POST /api/auth/register`, затем вход)

3.1. Email должен быть похож на адрес («name@domain.tld»), иначе «Введите корректный email».
3.2. Пароль от 8 до 128 символов, иначе «Пароль должен быть не короче 8 символов».
3.3. Поле «Повторите пароль» должно совпадать, иначе «Пароли не совпадают». До исправления запрос не отправляется.
3.4. Ответ 409: рядом с полем email «Этот email уже зарегистрирован», введённые значения остаются.
3.5. Во время отправки действует правило 2.2.
3.6. При успехе выполняется автоматический вход и переход на `/subscriptions` с сообщением «Аккаунт создан».

## 4. Список подписок (`GET /api/subscriptions`)

4.1. Загрузка: на месте списка индикатор и текст «Загружаем подписки…», у контейнера `aria-busy="true"`.
4.2. Пустой ответ: «Подписок пока нет» и кнопка «Добавить подписку».
4.3. Успех: у каждой подписки название, сумма с валютой, период оплаты (по-русски), следующая дата списания и «через N дней», стоимость в месяц.
4.4. Ошибка загрузки: сообщение «Не удалось загрузить подписки» и кнопка «Повторить», которая заново делает запрос.
4.5. Неактивные подписки (`is_active = false`) помечены «Приостановлена».

## 5. Добавление подписки (`POST /api/subscriptions`)

Форма открывается в диалоге по кнопке «Добавить подписку».

5.1. Поля и правила:

| Поле | Правило | Сообщение |
|---|---|---|
| Название | обязательно, пробелы по краям обрезаются, строка из пробелов не подходит, не больше 255 символов | «Введите название» |
| Сумма | число больше 0, не больше двух знаков после запятой | «Сумма должна быть больше 0» |
| Период оплаты | выбор: месяц, год, неделя, свой интервал в днях | |
| Интервал в днях | поле видно только для «свой интервал», обязательно, целое от 1 до 3650 | «Введите число дней от 1 до 3650» |
| Дата начала | обязательна, от 2000-01-01 до 2100-12-31 | «Укажите дату начала» |
| Заметка | необязательно, до 500 символов | |

5.2. Если есть ошибки валидации, запрос не отправляется, сообщения показываются рядом с полями, фокус уходит на первое неверное поле.
5.3. Во время сохранения кнопка заблокирована и показывает «Сохраняем…», поля заблокированы, закрыть диалог нельзя. Повторный клик или Enter второй запрос не создают.
5.4. При успехе (201) диалог закрывается, новая подписка видна в списке, показывается сообщение «Подписка добавлена». Форма при следующем открытии пустая.
5.5. При ответе 422 сообщения сервера показываются рядом с соответствующими полями.
5.6. При других ошибках (5xx, сеть) в диалоге сообщение «Не удалось сохранить. Повторите попытку». **Введённые значения остаются в полях точно такими, как были.**
5.7. Esc и кнопка «Отмена» закрывают диалог без запроса (когда не идёт сохранение).

## 6. Доступность и клавиатура

6.1. У каждого поля есть подпись (`label`). Ошибка связана с полем (`aria-describedby`, `aria-invalid`), общие ошибки формы объявляются (`role="alert"`).
6.2. Весь основной сценарий проходится только с клавиатуры: Tab, Shift+Tab, Enter, Esc.
6.3. Текущий фокус виден на любом элементе управления.
6.4. В диалоге фокус не уходит за его пределы, при закрытии возвращается на кнопку «Добавить подписку».
6.5. На ширине 360 px нет горизонтальной прокрутки, элементы управления доступны.
6.6. Контраст текста не ниже 4,5:1, границ полей ввода и кольца фокуса не ниже 3:1 (значения в `design-system.md`, раздел 7).
6.7. Мигающее подчёркивание у заголовков-eyebrow и дрейф свечения отключаются при `prefers-reduced-motion: reduce`.
6.8. Ошибка и успех передаются не только цветом: рядом есть текст (и значок), поэтому сообщение понятно без различения цветов.

## 7. Соответствие API

Формат данных тестовых ответов совпадает с реальным API бэкенда:

- сумма приходит строкой (`"9.99"`), даты строкой `YYYY-MM-DD`;
- элемент списка: `id`, `name`, `amount`, `billing_cycle`, `custom_interval_days`, `is_active`, `start_date`, `next_billing_date`, `note`, `monthly_cost`, `charge_date`, `days_until`;
- имена полей в `snake_case` преобразуются в `camelCase` только в слое API;
- ошибки: `{"detail": "..."}` (401, 409) и список ошибок для 422.

## 8. Приёмка

- После ответа API 500 при сохранении в поле «Название» остаётся точная введённая строка (5.6).
- Два быстрых клика по «Добавить» дают ровно один запрос (5.3).
- Вход с неверным паролем показывает сообщение и сохраняет введённый email (2.3).
- Сценарий «вход → добавить подписку → запись в списке» проходится автоматическим тестом и вручную с клавиатуры.
